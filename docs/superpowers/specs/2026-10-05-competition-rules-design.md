# 申报通：结构化竞赛规则库设计

日期：2026-10-05。状态：待用户审阅，尚未实现。

## 1. 目标与本轮范围

用户希望计算机相关专业学生能先找到适合自己的比赛，再询问具体内容、要求和网址。已选路线为“结构化竞赛库＋原文检索”，并同意先完成竞赛数据表、规则编辑确认页和首批三个赛事的数据录入验证。

本轮交付是可追溯的规则维护模块，为后续推荐、资格核验和申报清单提供可信数据。包含赛事及赛道建档、规则草稿编辑、字段原文依据、确认发布和三个赛事的本地资料验证。

首批赛事：计算机设计大赛、蓝桥杯、中国软件杯。采用已经导入的真实资料，缺失信息保留“待确认”。首轮选取计算机设计大赛的软件应用与开发、蓝桥杯软件赛 Python 和中国软件杯 A 组；不声称覆盖各母赛事全部赛道。

本轮不实现专业推荐算法、学生资料表、自动资格结论、清单导出、定时抓取或公网部署。这些是后续独立模块。AI 自动提取规则草稿也放到维护流程验证之后；本轮通过人工整理的草稿和可编辑表单验证数据结构及证据约束。

## 2. 现状与方案选择

现有 Next.js 项目使用 SQLite 保存 documents、chunks 和 answers。原文导入、网址抓取、引用问答和多轮追问已经运行；数据库尚无结构化竞赛规则表。当前服务是单人本地工作台。

可选路线：

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 在现有数据库新增规则与依据，人工确认后发布（采用） | 复用原文定位、删除和事务能力；可检查每个条件 | 需要编辑和确认页面 |
| 仅给原文补标签，再直接让模型推荐 | 开发快 | 无法可靠计算人数、区分未知条件或解释筛选依据 |
| 另建图数据库与自动采集管理系统 | 可表达复杂关系 | 首批三项赛事不需要这套运维和同步机制 |

采用增量扩展。继续使用现有模型配置、数据库和接口习惯，不新增数据库服务或模型费用。

## 3. 用户流程

工作台新增“竞赛规则”入口，与“知识问答”“资料库”“运行设置”并列。

1. 查看赛事列表，按赛事、届次、赛道和发布状态区分记录。
2. 新建或打开一条赛道记录，选择已经导入的适用资料。
3. 编辑规则字段，选择支持该字段的原文片段；旁边显示全文、页码或段落及来源网址。
4. 对有值的字段逐项确认；没有依据的字段标记未知，冲突字段保留双方依据和说明。
5. 保存草稿。发布时展示已确认字段、未知字段和待处理问题，由维护者点击“确认发布”。
6. 列表展示最新有效发布版本；修改已发布规则生成新草稿，旧版本保持可追溯。

维护者确认只表示已核对资料，不代表学校审核或组委会正式批准参赛。草稿界面和发布详情均明确届次与阶段。

## 4. 数据结构

### 4.1 四张新增表

| 表 | 职责 | 主要字段 |
| --- | --- | --- |
| competitions | 母赛事档案 | id、name、aliasesJson、catalogNumber、catalogYear、createdAt |
| competition_events | 某届某赛道某阶段 | id、competitionId、editionLabel、yearStart、yearEnd、trackName、stage、sourceDocumentIdsJson、createdAt |
| competition_rule_versions | 可审核的规则版本 | id、eventId、version、status、bodyJson、editRevision、createdAt、updatedAt、publishedAt |
| competition_rule_evidence | 字段与原文关系 | id、versionId、fieldPath、documentId、chunkId |

外键关联现有 documents 与 chunks；赛事、赛道和版本使用稳定 ID。表通过幂等初始化加入现有数据库，不重建或覆盖原始资料。

同一个 event 的 version 唯一；同时最多一份草稿和一份当前发布版本。保存草稿需要 expectedRevision，事务内递增 editRevision；版本过旧返回 409 并提示重新载入，避免不同窗口覆盖编辑。发布版本内容不可直接修改。

sourceDocumentIdsJson 是该赛道允许引用的资料集合，服务端验证每个文档存在。资料的赛事、届次和适用阶段须在建档时核对；共用母赛事规则可以关联至同届多个赛道，跨届资料不能直接当成本届资格规则。跨届或标题不明确的资料，界面要求补充适用说明；存在无法解决的适用冲突时不允许发布确定结论。

### 4.2 规则正文

bodyJson 使用明确的 TypeScript 类型与服务端验证，禁止执行表达式或任意规则脚本。字段分组如下：

| 分组 | 字段 |
| --- | --- |
| 内容说明 | summary、contestFormat、entryPath、technicalRequirements |
| 学生条件 | studentLevels、fullTimeRequired、majorRestrictions、gradeRestrictions |
| 团队条件 | studentMin、studentMax、teacherMin、teacherMax、totalTeamMax、teachersCountTowardTotal、sameSchoolRequired、teacherRequirements |
| 时间事项 | deadlines：名称、阶段、日期或时刻、时区、精度 |
| 提交材料 | materials：名称、必交/可选/未知、适用阶段、补充条件 |
| 推荐标签 | majors、skills、interests、维护者解释 |
| 学校分类 | schoolName、category、basisYear、认定状态及说明 |

规则字段统一记录 value、state、note，state 为 unknown、unreviewed、confirmed 或 conflict。依据由 evidence 表按 fieldPath 关联，例如 team.studentMax 或 deadlines.registration。重复项使用稳定 itemId，排序不会改变依据归属。

- unknown 的 value 为 null，不能解释为“无限制”“不要求”或“允许”。
- “不限专业”需要原文明确依据；仅未写专业条件只能表示未知。
- 数值是非负整数，最小值不得大于最大值。总人数和学生人数分开；指导组名额与实际教师人数也不能混为一谈，可用 teacherRequirements 说明尚未建模的例外。
- 日期采用 Asia/Shanghai。原文只有日期时保留 YYYY-MM-DD 和 date 精度，不补造 23:59；精确时刻使用带 +08:00 的 ISO 时间。报名截止、作品提交和竞赛日期分别保存。
- 推荐标签是维护者建议，有说明和维护者确认，不当作官方专业限制。
- 学校类别需要独立依据与适用年度。2024 目录不能自动确认 2026 的学校 B 类认定；学校类别未知不阻止其他已确认规则发布。
- 来源网址从文档读取，不让模型或表单输入另一个“证据网址”。赛事官网入口可作为非规则元数据单独保存并验证为 HTTP/HTTPS。

JSON 总体最多 64KB；字符串、列表数量和数值范围有服务端上限。草稿支持不完整字段；类型、格式和数值关系错误在保存时阻止。

## 5. 证据与发布约束

原文选择器复用现有文档详情接口与片段定位。维护者为有值的官方规则字段绑定至少一个片段。证据由服务端确认：chunk 存在、属于指定 document，并且 document 在本赛道选择的资料集合内。

程序能验证片段身份和归属，不能仅凭 ID 判断原文是否真正支持字段值。界面必须展示原文并要求维护者确认；人工核对作为本轮发布前提。

发布需要：

1. 至少一份有效关联资料，且至少一项内容或资格字段已确认。
2. 每个有值的官方规则字段均为 confirmed，且具有有效原文依据。
3. 推荐标签有维护者说明并已确认；所有 unknown 字段明确保留为待确认。
4. 不存在 unreviewed、conflict 或无法解决的届次/阶段适用问题。
5. 每个必交材料、每个日期条目独立满足依据与确认条件。

允许发布信息不完整的记录，但详情明确展示资料完整度和未知条件。发布不等于已符合资格，也不等于当前开放报名；已过日期标为历史信息，未知日程不推算下一届。

状态：draft → published；新的草稿发布后，先前 published → archived。来源被删除时，所有引用该来源的 published/archived 版本变为 needs_review，草稿的对应字段撤销确认。needs_review 不供后续推荐和核验读取。

删除原文与撤销规则依据在同一个 SQLite 事务内完成。删除 evidence 关系，不另外保留正文快照，避免“删除资料”后仍保存被删除的原文。历史规则值可在维护页显示，但注明失去依据，不能继续显示为已确认。发布事务再次检查来源，避免编辑期间来源已删除却仍成功发布。

删掉当前版本的来源后不自动回退到旧版本，因为旧版本可能已经被延期通知替代。必须补充来源并重新审核发布。

## 6. 接口与代码边界

新增 server/competitions/types.ts、validation.ts、store.ts，分别负责类型、规则校验和数据操作；使用现有 KnowledgeStore 的数据库连接与事务边界，不在第二连接中异步处理删除失效。

| 接口 | 用途 |
| --- | --- |
| GET /api/competitions | 赛事、赛道、最新发布状态及草稿摘要 |
| POST /api/competitions | 新建母赛事或同母赛事的赛道记录 |
| GET /api/competitions/events/[id] | 赛道详情、版本、字段与有效依据 |
| POST /api/competitions/events/[id]/draft | 从当前有效版本创建草稿，或创建空草稿 |
| PUT /api/competitions/versions/[id] | 按 expectedRevision 保存字段、资料集合和依据 |
| POST /api/competitions/versions/[id]/publish | 重新校验并原子发布 |

资料集合的编辑随草稿保存提交；competition_events 展示最新有效发布版本对应的集合，未发布变更仅在草稿中生效。草稿 body 同时保存适用资料 ID 与适用说明，发布事务同步 event 的集合；因此编辑草稿不改变当前发布版本的依据。

所有写接口沿用 checkOrigin；只允许本地工作台，不新增账户或远程管理入口。返回完整可展示错误，版本冲突返回 409，目标不存在返回 404，输入不合法返回 400。

前端新增独立 competition-library.tsx 与 rule-editor.tsx，Workspace 仅增加入口、切换和调用。复用现有颜色、表单和原文弹窗风格；桌面左右显示字段及依据，手机按顺序展开，保证键盘访问与错误提示。规则维护不要求用户输入 API 密钥。

问答接口保持当前行为。本轮规则详情可以跳转至知识问答并选择该赛道适用文档；程序推荐与资格核验稍后只消费最新有效发布版本。

## 7. 首批数据与复现

首批草稿从已导入资料整理，使用来源 URL、正文哈希和原文锚点定位证据，不把本机 UUID 固化到源码。

| 赛事范围 | 采用资料 | 必须验证的区别 |
| --- | --- | --- |
| 计算机设计大赛：2026 第19届，软件应用与开发 | 参赛要求与分类要求 | 本科生、同校、学生人数与教师人数；国赛上推资格不是直接报名 |
| 蓝桥杯：2025—2026 第17届，Python 软件赛 | Python 规则与省赛时间通知 | 单人科目与组别；省赛日期不能当作报名截止；不外推第18届 |
| 中国软件杯：2026 第15届，A组，报名与初赛提交 | 报名说明、延期通知、作品提交说明 | 总名额包含指导教师/指导组；A/B组学生层次不同；延期后的时间与原日程分开 |

补充日期和材料仅采用已取得原文；未取得当届校内通知，学校阶段截止与当年度 B 类认定保留 unknown。已知届次是历史验证资料，不显示成现在仍可报名的赛事。

新增本地录入脚本和公共来源映射：脚本通过同样的数据校验创建 draft，不自动 confirmed 或 published。缺少原文、正文哈希变化、锚点不唯一或同名不同届时停止相应条目录入并提示核对。反复执行不创建重复赛事、赛道或草稿，不覆盖已经人工修改的草稿。

GitHub 中只提交代码、空密钥配置、公开来源映射、必要的规则草稿数据与验收说明。数据库、PDF、抓取正文、密钥和真实问答输出继续保留在被忽略的本地目录。空数据库启动仍能建档，原文未导入时显示采集入口和待补资料。

## 8. 验收标准

功能验证：

- 能新建赛道、保存草稿、重新载入、绑定原文、确认发布和创建下一版本。
- 未确认字段、冲突字段、错误来源、无依据数字和跨届误用不能变成确定发布规则。
- null 与“不限”、学生人数与总人数、报名日期与省赛日期分别显示。
- 未完成的草稿不影响已发布版本；过期窗口保存不覆盖新编辑。
- 删除来源后，关联规则立即失效；发布与删除竞争不会留下有效但无来源的版本。
- 原有导入、删除、问答和引用定位仍能运行，旧数据库数据保持不变。
- 三个赛事各完成“草稿→核对原文→发布→查看依据”真实操作，重启后数据仍在。
- 空库与重复录入可复现；手机页面无水平溢出、表单可键盘操作。

验证方法：规则校验、发布事务、版本冲突、来源删除及重复录入采用针对边界的自动化测试；原有回归、类型检查和生产构建通过。页面用实际操作验证，事实值由维护者逐条对照原文。仅检查引用 ID 不计作事实正确率。

## 9. 下一阶段接口

本轮完成后，推荐模块按专业、兴趣、技能筛选有效发布记录，输出“相关候选”和“资格待确认”，保留历史/当前届次区别。资格模块再用明确数字和条件计算满足、不满足、缺信息或规则待确认；申报清单使用独立材料和日期条目。各模块以 versionId 绑定规则版本，以便后续通知更新时识别受影响结果。
